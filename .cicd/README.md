# Generic CI/CD framework

One reusable pipeline ([.github/workflows/ci-cd.yaml](../.github/workflows/ci-cd.yaml)) drives
every project type — React, Angular, Java, .NET, Python, PHP, Rust, Node.js, or
anything else that fits the same shape. Per-project behavior comes entirely from
`.cicd/config.yml`; nothing project-specific is hardcoded in the workflow. Most of
that config doesn't even need to be written by hand — `project.language` and
`build.tool` are auto-detected from marker files (`pom.xml`, `package.json`,
`Cargo.toml`, `requirements.txt`, ...) when config.yml doesn't set them explicitly.
See "Auto-detecting project structure" below.

## Folder structure

```
.cicd/
  config.yml                 # THIS project's pipeline config (edit this per repo)
  config/                    # Reference examples for other stacks — copy one over config.yml
    react.yaml
    angular.yaml
    java-maven.yaml
    java-gradle.yaml
    .net.yaml
    python.yaml
    php.yaml
    rust.yaml
  environments/               # Per-environment overrides, merged on top of config.yml
    dev.yml
    qa.yml
    prod.yml
  mappings/                   # Framework-owned lookup tables — extend these to add a new stack
    defaults.yml              # Fallback values for anything config.yml omits
    runtimes.yml               # language -> toolchain family + supported versions
    package-managers.yml       # build.tool -> default install command
    deployment-types.yml       # deployment.type/target -> requirements + implementation status
    artifact-repository-formats.yml  # artifactRepository.format -> requirements + implementation status
  scripts/                     # Stage logic, called from the workflow, all config-driven
    lib/common.sh               # shared: yq install, config merge/read, GITHUB_OUTPUT helper
    detect-project.sh           # marker-file -> language/tool/framework/name guesses
    validate-config.sh
    setup-runtime.sh
    install-dependencies.sh
    lint.sh
    test.sh
    build.sh
    package.sh
    sonar.sh
    security-scan.sh
    docker.sh
    deploy.sh
    nexus.sh
  output/                      # Created at build time by package.sh — the staged artifact
  .detected.yml                # Generated by detect-project.sh at run time — gitignored, never committed
```

## How a project is configured

`config.yml` is the single input file. Fields map directly to pipeline behavior:

| Field | Meaning |
|---|---|
| `project.name` / `projectType` / `language` / `framework` | Identity — `language` selects the toolchain setup step and is validated against `mappings/runtimes.yml`. All four are auto-detectable; see below |
| `runtime.version` | Passed to the matching `actions/setup-*` step. Auto-detectable (defaults to the newest `supportedVersions` entry for the resolved language) |
| `build.tool` | Selects install/build/test defaults (`npm`, `yarn`, `pnpm`, `maven`, `gradle`, `dotnet`, `pip`, `poetry`, `composer`, `cargo`). Auto-detectable |
| `build.packageManager` | Informational / for future package-manager-specific tuning |
| `build.installCommand` / `buildCommand` / `testCommand` / `lintCommand` | Override the tool's default command; leave unset to use the mapped default |
| `build.artifactPath` | What `package.sh` stages into `.cicd/output/` for upload (globs OK, e.g. `target/*.jar`) |
| `build.coveragePath` | Used by `sonar.sh` to point Sonar at the right coverage report |
| `quality.sonarEnabled` | Gates the `sonarqube` job |
| `security.securityScanEnabled` / `filesystemScan` / `dependencyScan` / `containerScan` | Gate the `security` job and the image scan step in `docker` |
| `docker.enabled` / `dockerfile` / `imageName` / `registry` | Gates the `docker` job; `registry: ghcr` resolves to `ghcr.io/<owner>` |
| `deployment.enabled` / `type` / `target` / `environment` / `container.*` | Gates the `deploy` job; `type`/`target` validated against `mappings/deployment-types.yml` |
| `artifactRepository.enabled` / `type` / `format` / `url` / `repository` / `groupPath` / `version` | Gates the `nexus` job; `format` validated against `mappings/artifact-repository-formats.yml` |

Every field has a static default in `mappings/defaults.yml`, a structure-based
guess from `detect-project.sh`, or both — **except** `project.name` (falls back
to the repo name), and `project.language`/`build.tool` (no safe default; fail
the run with a clear error if neither `config.yml` nor detection can supply
them). Everything else can be omitted from `config.yml` entirely.

## How defaults and validation work

`scripts/lib/common.sh` provides `cfg <config_file> <yq_path> [fallback]`,
which reads a three-layer merge, lowest to highest precedence:
`mappings/defaults.yml` (static fallbacks) → `.cicd/.detected.yml`
(structure-based guesses, see below) → `config.yml` (always wins). Every
script sources this lib and calls `cfg` instead of parsing YAML directly, so
default/detection handling lives in exactly one place.

The `validate` job in the workflow runs first and:
1. Runs `detect-project.sh` (see below) so detected values are available to
   every later job.
2. Fails if a required field (`project.name`/`language`, `build.tool`) is
   missing after defaults + detection + config.yml are all applied.
3. Fails if `project.language` isn't in `mappings/runtimes.yml`, or `build.tool`
   isn't in `mappings/package-managers.yml`, or (when deployment is enabled)
   `deployment.type`/`target` aren't in `mappings/deployment-types.yml`.
4. Defaults `runtime.version` to the newest documented `supportedVersions`
   entry for the resolved language if it's still unset; warns (non-fatal) if
   an explicitly-set version isn't in that list.
5. Prints the fully resolved config and exposes the values every later job
   needs as **job outputs**, so downstream jobs gate stages with plain
   `if: needs.validate.outputs.x == 'true'` instead of re-parsing YAML.

## Auto-detecting project structure

`scripts/detect-project.sh` looks for one marker file at the repo root and
writes `.cicd/.detected.yml` accordingly:

| Marker file | Detected `language` / `tool` / `framework` |
|---|---|
| `pom.xml` | java / maven / spring-boot |
| `build.gradle`, `build.gradle.kts` | java / gradle / spring-boot |
| `Cargo.toml` | rust / cargo / cargo |
| `*.csproj`, `*.sln` | csharp / dotnet / aspnetcore |
| `composer.json` | php / composer / laravel (if `laravel/framework` is a dependency) or php |
| `package.json` | javascript or typescript (if `tsconfig.json` exists) / npm, yarn, or pnpm (by lockfile) / react, angular, next, vue, or node (by dependency) |
| `pyproject.toml` | python / poetry (if `[tool.poetry]`) or pip / python |
| `requirements.txt`, `Pipfile` | python / pip / python |

It also guesses `project.projectType` (`frontend` for react/angular/vue/next,
`backend` otherwise), defaults `project.name` to the GitHub repository name
(or the checkout directory name outside Actions), and defaults
`runtime.version` to the newest `supportedVersions` entry in
`mappings/runtimes.yml` for the language it detected.

This only ever **fills gaps** — every detected key is layered strictly under
`config.yml` (see "How defaults and validation work"), so any field you set
explicitly is never touched. It runs once per job (`lib/common.sh`'s
`ensure_detected` skips it if `.cicd/.detected.yml` already exists) since every
job starts from a fresh checkout and the file is gitignored, never committed.

If no marker file matches and `config.yml` doesn't set `project.language`/
`build.tool` either, `validate-config.sh` fails with a message telling you to
either set the field explicitly or add a recognized marker file — it never
silently guesses wrong or runs with an empty toolchain.

## How the pipeline adapts per stack

Two mechanisms, matched to what each stage actually needs:

- **Config-driven scripts** (install/lint/test/build/package/sonar-properties/
  security-resolve/docker-meta/deploy-resolve): pure bash, keyed off `build.tool`
  or `project.language` via a `case` statement, reading commands from
  `config.yml` with a mapped default fallback. Adding a stack here means adding
  one `case` arm plus (if needed) one row in a `mappings/*.yml` file.
- **Toolchain install** (Node/Java/.NET/Python/PHP): the workflow runs the
  matching official `actions/setup-*` step, gated by
  `if: needs.validate.outputs.language == '<language>'`. This is intentionally
  a workflow-level conditional, not a script, because these actions need to run
  as real Action steps (PATH/cache wiring) — a shell script can't do that.
  Adding a language here means one more `if:`-gated step in `build-test`, plus
  an entry in `mappings/runtimes.yml`.

Both are additive: existing stacks are untouched when a new one is added.

## Onboarding a new project

1. Copy the closest example from `.cicd/config/` to `.cicd/config.yml` at the
   repo root (or wherever `CONFIG_FILE` in the workflow points).
2. Fill in `project.name`, `runtime.version`, and any command overrides your
   project needs.
3. Copy `.github/workflows/ci-cd.yaml` into the new repo unchanged.
4. Set the secrets the enabled stages need (`SONAR_TOKEN`/`SONAR_HOST_URL` for
   Sonar; `VPS_HOST`/`VPS_USER`/`VPS_SSH_KEY` for a `container`/`vps` deploy).

## Adding a new technology stack

1. Add the language to `mappings/runtimes.yml` (`setup:` family +
   `supportedVersions`).
2. Add the build tool to `mappings/package-managers.yml` (default install
   command).
3. Add a `case` arm for the tool in `scripts/build.sh` and `scripts/test.sh`
   (skip if the project always sets `buildCommand`/`testCommand` explicitly).
4. If the language needs a real toolchain install, add one `if:`-gated
   `actions/setup-*` step to the `build-test` job.
5. Add a marker-file `elif` branch to `scripts/detect-project.sh` so projects
   don't have to set `project.language`/`build.tool` by hand (optional, but
   that's the whole point of auto-detection — skip it and the stack still
   works, just requires an explicit config.yml every time).
6. Add a sample config under `.cicd/config/` for future projects to copy.

No existing script's control flow changes — steps 1-6 are additive.

## Adding a deployment target

`mappings/deployment-types.yml` documents every `type`/`target` combination
this framework recognizes and validates against, but `scripts/deploy.sh`
currently *implements* only `container` + `vps` (SSH + `docker run`, wired to
the workflow's `appleboy/ssh-action` step). Deploying to `kubernetes`, `s3`,
`eks`, etc. means: extending `deploy.sh`'s resolve step with that target's
values, adding a matching `if:`-gated step in the `deploy` job, and flipping
`implemented: true` in `deployment-types.yml`. Until then, validation accepts
those values but the deploy job fails with an explicit message telling you
what to implement — it never silently no-ops a deployment.

## Publishing to an artifact repository

`artifactRepository.enabled` gates a standalone `nexus` job that runs right
after `build-test`, in parallel with `sonarqube`/`security` — independent of
`deployment`, since publishing a build artifact and deploying a running
service are different concerns (a library build might publish but never
deploy; a container deploy might not need to publish anywhere). It downloads
the `application-artifact` uploaded by `build-test` and hands
`.cicd/output/` to `scripts/nexus.sh publish`, which requires `NEXUS_USERNAME`
and `NEXUS_PASSWORD` secrets.

`scripts/nexus.sh` implements `artifactRepository.format: raw` end-to-end: a
plain `curl --upload-file` `PUT` of every file in `.cicd/output/` to
`<url>/repository/<repository>/<groupPath>/<version>/<relative-path>` on a
Nexus "raw" hosted repository. `groupPath` defaults to `project.name` and
`version` defaults to the commit SHA, both overridable in `config.yml`. Raw
works for any artifact type (jar, wheel, nupkg, zip, tarball) since Nexus
doesn't validate the file layout for raw repos — it's the generic fallback,
not a Maven/npm/PyPI-protocol publish.

### Adding an artifact repository format

`mappings/artifact-repository-formats.yml` lists every `format` value
validation accepts (`raw`, `maven2`, `npm`, `pypi`, `nuget`, `composer`).
Only `raw` is implemented. To add real `maven2`/`npm`/etc. protocol support:
extend `scripts/nexus.sh`'s format check with the new logic (or call a
dedicated action, e.g. an `mvn deploy:deploy-file` step, from the `nexus` job
instead), then flip `implemented: true` for that format. Until then,
validation accepts the value but `nexus.sh` fails loudly rather than
silently uploading nothing.

## Sample configs

See `.cicd/config/` for working examples: `react.yaml`, `angular.yaml`,
`java-maven.yaml`, `java-gradle.yaml`, `.net.yaml`, `python.yaml`, `php.yaml`,

## Legacy pipeline

The React-only pipeline this framework replaced (`ci-cd-old.yaml`) has been
removed — it triggered on the same `push` events as `ci-cd.yaml`, so every
push ran both, and its hardcoded SonarQube step had no relation to this
framework's config-driven one. If you need to see what it looked like, check
git history before it was deleted.
